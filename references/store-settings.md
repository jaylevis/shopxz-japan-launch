# 店铺基础配置：后台九项设置

此阶段对应商家后台的基础、高级、TASK、验证码、支付、交易、税费、国家与物流菜单。整站上线必须逐项有当前值、目标值、处理结果和证据，不能以“应用配置已完成”代替。

新profile的 `store_settings` 从 `assets/store-settings.json`加载，由 `modules.basic` 控制。旧profile没有这组字段时保留原先检查/Agent流程，不自动增加线上写入。字段含义、方法和参数仍以管理技能当前api-doc为准。

## 1. 基础设置

- 设置本站品牌、客服邮箱、已上传的Logo/favicon、日语和Asia/Tokyo。
- 语言、货币和时区必须在当前可选池中；只有存在于世界语言列表不等于该店已经启用。
- 品牌输入为空时复用有效现值，不拿空字符串擦除已有Logo/邮箱。
- `basic_set`是全量接口；保留站点开关、订单编号前后缀、游客查询和handle规则等未指定字段。
- 站点已关闭时先保持关闭，页面及经营验收后才按发布范围开放；配置基本信息不提前开放交易。
- JPY由单独的默认币种接口设置，basic_set不包含币种。实际币种不为JPY时，先核对已上传商品的金额口径；资料中明确 `allow_currency_change=true` 才生成币种变更。该动作不换算商品数字，也不批量改价。
- 如果已开启多币种应用，更改默认币种后还必须更新以新默认币种为基准的汇率。检查应用及现有币种配置，按当前currency文档重新定基准并核对显示金额；未核实前保留待办，不称币种阶段全部完成。

CLI以应用列表和已启用币种识别多币种风险，并生成汇率后续任务；它不计算新汇率，也不直接读取或保存该应用的配置。Agent通过 `currency/get`核对实际开关和汇率，再按当前 `get-rate/set`文档完成重新定基准与前台金额检查。应用存在本身不证明其开关已开启。

读/写路由：`system-settings/basic_get → basic_set`、`basic_set_currency`；枚举池为 `shop-info/languages/currencies/timezone_list/country_list`。前三者在当前版本是**只读POST**，不能误当成写设置，也不能据此允许任意POST绕过写入门禁。

## 2. 高级设置

核对搜索模式、匹配方式、文件下载方式、图片referrer设置、Liquid调试模式。默认保持现状；只提交显式选择的修改，并保留其余完整字段。

日语搜索先实际试搜；不凭其他语言经验盲切全文搜索。调试模式适合装修阶段，正式上线前按发布阶段需求关闭。图片referrer策略同时检查商品图、邮件和外部抓取，不能复制标准站后导致图片加载失败。

路由：`system-settings/advance_get → advance_set`。

## 3. TASK设置

标准建议 `reflush_cache_type=2`：任务完成后刷新缓存。1是持续自刷新，3需要任务完成后另行刷新；保留商家显式采用的特殊运维安排。

此项配置任务后的缓存行为，不等于执行、删除或清空任务队列。读取设置不触发刷新；实际装修/配置提交完成后按管理技能刷新所需缓存。

路由：`system-settings/task_get → task_set`；页面缓存只读检查 `cache_get`，装修缓存按装修工作流处理。

## 4. 验证码设置

检查后台登录、注册、联系表单、评论及B2C询盘的保护。默认保留现有安全策略；需要调整才写显式字段，不能一键关闭所有验证。

长度为4/5/6，字符类型和过期秒数按API枚举。这里的**图片验证码过期时间不是游客邮件验证码有效期**，不得拿它写进邮件承诺。设置后验证相关表单可正常提交，不为验证而向商家发送无授权消息。

路由：`system-settings/captcha_get → captcha_set`。

## 5. 支付设置

先获取全部与已激活方式。保留已工作的渠道，按本站经营需求选择支持日本市场的渠道，不把案例站的某一服务商当所有新站默认。

资料包含所选方式代码及账号已核对的证据。`credentials_verified_codes`仅记录已经核对配置的**支付方式代码**，不是任何凭据；不得因字段名将公开方式代码列表误脱敏成字符串。未核对账号时列为待配置，不能只开一个空网关。

已核对的选定渠道可以通过 `payment/update-status`启用，并按需要 `set-top`。使用list返回的code，不用数据库ID代替payment_method；不关闭没有被本次选中的原有渠道。

支付模块目前没有适用于全部服务商的账号保存接口。缺少相应渠道凭据配置API时，按管理技能知识库定位后台页面，由商家填写或使用明确支持的渠道接口；不能自创端点。凭据不进profile、快照报告或技能包。

回读激活和顺序只是配置验证；支付跳转、日元金额、失败提示及退款能力另行按授权实测。

## 6. 交易设置

日本消费者预设：

| 字段 | 建议值 | 含义 |
|---|---:|---|
| login_account | 1 | 会员与游客均可购买 |
| deduct_stock | 2 | 成功下单时扣减；实际库存策略按业务调整 |
| checkout_page_type | 1 | 快速结账页：配送与支付方式合并为一步（仅Vue主题生效） |
| product_status_check | 2 | 商品下架后强校验，避免继续购买 |
| contact_type | 5 | 邮箱和电话必填；经营需要时可改为4等枚举 |
| name_type / name_require_type | 2 / 2 | 姓名分开填写且均必填 |
| address_company | 3 | 公司字段隐藏 |
| address_street_2 | 3 | 第二行地址隐藏；建筑物、房间号写在第一行地址 |
| address_zip | 1 | 邮编必填 |
| customer_can_cancel_order | 1 | 允许顾客取消，按业务需要调整 |
| pending_order_cancel_datetime | 0 | 不自动取消；不能与长期召回冲突 |

当前API的 `product_status_check=1`是“不校验”，不要把1想当然视为“开启保护”。`pending_order_cancel_datetime`单位是**秒**，召回延时单位是**分钟**。若订单1小时自动取消而邮件在1天后才发，方案不一致；应调整已授权的交易规则或召回节奏，不能宣称14天召回可用。

`checkout_page_type`与`coupon_show_type`只对Vue主题有效。预设把`checkout_page_type`设为1（快速结账页）；Liquid主题保存该值但页面仍为一页结账，不把字段变化当作页面已经发生变化。`coupon_show_type`保留原值。

第二行地址隐藏后，结账页提示与日本结账应用须引导顾客把建筑物名和房间号填进第一行地址；保存后用日本地址实测一次，确认不丢失房间号。

路由：`system-settings/checkout_get → checkout_set`。全量保存，提交前检测并发修改，之后回读并检查实际表单。

## 7. 税费设置

检查日本基础税费与可能覆盖它的自定义税费及适用商品。默认preserve，不统一设置0或10。税率单位遵守API（百分点），税率值由商家经营事实提供。

`prices_include_tax`是价格口径，不自动等于关闭税费引擎，也不授权再次加税。含税文案、商品价格、Feed与结账总额应一致。

明确提供税率后，生成具体 `tax/base-save`等请求：country_code、country_tax以及完整省级例外。保留未要求删除的省级税率和自定义方案，不能只提交一行而擦掉其余规则。

这些接口带管理技能门禁。方案须包含当前记录、目标税率、受影响范围、请求内容及回读方法；经适用授权和门禁执行后再报告已设置。API保存税率和启用税费状态是不同动作，分别核对。

## 8. 国家设置

日本单市场预设：`status=2`、`countrys=["JP"]`、`sorts=["JP"]`，代码来自实时国家池。完整保存并核对结账地址的国家选择。

这只控制配送国家选择，不等于屏蔽其他国家访客，也不能代替物流方案的日本覆盖。

路由：`system-settings/country_get → country_set`。

## 9. 物流设置

先读取全部方案、区域与费率，再生成精确差异；若存在多个日本方案或混合国家/重量公式，不自动挑一个覆盖，要求明确目标范围。

选择服饰示例时，目标是日本国内、价格计费：

| 商品小计 | 运费 |
|---|---:|
| 0 ≤ 金额 < 5,000 | 399 JPY |
| 5,000 ≤ 金额 < 配置上界 | 0 JPY |

运费API的start包含、end不包含。验证4999/5000/5001三点；这些是规则数学核对，实际结账另测。免邮门槛0表示全免邮；未知门槛不猜。上界使用资料中的明确大数，不称平台支持无穷值。

新建顺序：关闭状态的物流方案 → JP区域及费率 → 回读 → 启用方案。新ID由创建响应绑定，不能使用模板中的源站ID或把未解析占位提交到服务器。

更新时读取目标shipping_id/zone_id的完整信息，检查同一方案内已占用的国家/省份，再提交zone-update。`province=[]`代表该国全部省份，不能误认为没有省份。不同物流方式可以覆盖相同国家；不要把方案内冲突规则扩大为全店只能有一个日本物流方式。

不得删除其他国家、省份、重量/数量收费、偏远地区例外来套用示例。货物处理时间和运输时效分别写政策/Feed，不能编造物流运费接口没有的字段。

物流创建/区域保存/状态切换接口带管理技能门禁，本包输出具体 `backend_workflows` 请求和核验步骤供Agent执行；工具不会自制确认文件。执行前重新查当前值和区域占用，处理真实的确认挑战，再回读全部关系。未执行的方案保持“待执行”，不得算完成。

## 本阶段交付

九项各有状态：已符合、已修改并回读、保持现状、资料待补、门禁待执行、未知/冲突。基础语言/币种变更后重新采集，后续券与召回继续核对实际ja/JPY及SMTP，不能用预期值代替事实。按依赖推进应用和交易实测；独立的内容、装修工作可继续，未完成的支付、物流或税费核验仍列入上线缺口。
